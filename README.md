# wg-awg-relay

Linux-релей WireGuard / AmneziaWG для произвольного набора IPv4- и IPv6-подсетей за одним или несколькими исходящими пирами.

Проект использует официальный userspace-движок `amneziawg-go` как отдельный процесс. Криптографическая реализация протокола не копируется и не переписывается в этом репозитории.

## Реализованные компоненты

| Пакет | Назначение |
|---|---|
| `protocol` | Конфигурация WireGuard/AmneziaWG, проверка параметров, LPM, разрешение конфликтов и UAPI-кодек |
| `engine` | Синхронизация маршрутов с работающим устройством через UAPI, транзакционное обновление и откат |
| `platform/linux` | Запуск `amneziawg-go`, настройка TUN, policy routing, IPv4/IPv6 forwarding и nftables NAT |
| `app` | Сборка платформенных и протокольных компонентов в сервис релея |
| `control` | Локальный HTTP API через Unix-сокет |
| `cmd/wg-awg-relay` | CLI запуска и динамического управления маршрутами |

## Маршрутизация

- IPv4 и IPv6 используют единую модель `netip.Prefix`.
- Маршруты принимаются из `peers[].routes`, общего `routes` и `peers[].allowed_ips`.
- Все источники объединяются в `Config.EffectiveRoutes()`.
- Сначала выбирается наиболее длинный префикс (longest-prefix match).
- Приоритет сравнивается **только у маршрутов с одинаковым префиксом**.
- При равном приоритете используется детерминированное правило: лексикографически меньший идентификатор пира.
- При конфликте одинаковый префикс передаётся в UAPI только победившему пиру; префиксы другой длины сохраняются для LPM.

Если в конфигурации один пир, общий маршрут может не содержать поле `peer`. Если пиров несколько, поле `peer` обязательно.

## Динамические изменения

`engine.RouteController` применяет полную конфигурацию только при первом запуске. После этого `AddRoute` и `RemoveRoute` обновляют AllowedIPs конкретных пиров через `replace_allowed_ips`, не заменяя список пиров и не пересоздавая туннель.

При передаче одинакового префикса другому пиру сначала добавляется новый владелец, затем очищается прежний. При ошибке UAPI движок пытается восстановить прежние AllowedIPs. Платформенный менеджер маршрутов устанавливает новые системные маршруты до удаления старых и также выполняет попытку отката.

Изменение маршрутов не вызывает `conntrack -F` и не очищает NAT-состояние. Динамические изменения через CLI действуют до остановки процесса; они не записываются обратно в JSON-файл автоматически.

## Конфигурация

Полный пример: [examples/config.json](examples/config.json).

Основные поля:

- `private_key` — приватный ключ интерфейса (Base64 или hex); обязателен для запуска приложения;
- `listen_port` — UDP-порт устройства;
- `fwmark` — метка UDP-сокета WireGuard/AmneziaWG; приложение по умолчанию использует `51820`;
- `address` — адреса TUN-интерфейса;
- `mtu` — MTU интерфейса;
- `nat` — включение masquerade в отдельной nftables-таблице;
- `peers` — исходящие пиры, их `allowed_ips` и `routes`;
- `routes` — общие маршруты; при нескольких пирах указывайте `peer`;
- `amneziawg` — параметры обфускации и расширения AmneziaWG.

Поддерживаются параметры AmneziaWG 3.1, включая Header Protection, Content Padding, тайминги повторного handshake, случайные трейлеры и отключение cookie-пакетов. Для H1-H4 требуется Header Protection key; он должен быть 32-байтовым, а S1-S4 — не меньше 12. Диапазоны параметров проверяются до отправки в UAPI.

## Linux и безопасность маршрутов

Для запуска нужны права администратора, установленный официальный [`amneziawg-go`](https://github.com/amnezia-vpn/amneziawg-go) и `iproute2`. В `examples/config.json` ключи намеренно оставлены как заполнители — замените их на реальные ключи интерфейса и пиров перед запуском. Для `"nat": true` дополнительно нужен `nftables`.

Процесс запускается как `amneziawg-go -f <interface>`; по умолчанию UAPI-сокет находится в `/var/run/amneziawg/<interface>.sock`.

Системные маршруты устанавливаются в отдельную policy table. Правило `not fwmark <fwmark> lookup <table>` отправляет обычный трафик в туннель, но пропускает помеченные UDP-пакеты самого AmneziaWG через основную таблицу. Это предотвращает рекурсивную маршрутизацию VPN endpoint обратно в туннель.

При включённом NAT создаётся отдельная таблица `inet wg_awg_relay` и правило masquerade на выходном интерфейсе. Forwarding IPv4 включается при запуске; IPv6 forwarding — если конфигурация содержит IPv6-адреса или маршруты. Правила фильтрации цепочки FORWARD не изменяются: разрешение транзитного трафика должно соответствовать политике firewall хоста.

NAT-правило не пересоздаётся при динамическом изменении маршрутов. При запуске очищаются только устаревшие маршруты выделенной таблицы для этого интерфейса; при остановке удаляются управляемые маршруты и созданные самим менеджером policy rules; таблица NAT и системные sysctl намеренно не сбрасываются.

## Сборка и запуск

```sh
go test -race ./...
go vet ./...
go build -o wg-awg-relay ./cmd/wg-awg-relay
./wg-awg-relay validate -config examples/config.json
```

Запуск:

```sh
sudo ./wg-awg-relay run -config /etc/wg-awg-relay/config.json -interface awg0
```

Команды динамического управления из другого терминала:

```sh
sudo ./wg-awg-relay route add -prefix 10.30.0.0/16 -peer uplink-a -priority 10
sudo ./wg-awg-relay route remove -prefix 10.30.0.0/16 -peer uplink-a
sudo ./wg-awg-relay route list
```

Управляющий Unix-сокет по умолчанию: `/run/wg-awg-relay/control.sock`, права доступа — `0600`. Путь можно изменить параметром `-control-socket`.

GitHub Actions настроен на `go test -race ./...` и `go vet ./...`.

**Ограничения текущей версии:** приложение ориентировано на Linux; криптографию и пакетную обработку выполняет внешний `amneziawg-go`; автоматическое изменение firewall FORWARD и сохранение динамически добавленных маршрутов в исходный JSON пока не реализованы.
